# 序列帧渲染方案性能基线对比与定案

> 依据：`FrameAnimGpuTest`（Assets/Scripts/Game/Base/FrameAnim/FrameAnimGpuTest.cs）实测数据
> 配套：Game/FrameAnimGpu（SRP Batcher 版）、Game/FrameAnimGpuInst（Instancing 版）两个 shader
> 日期：2026-08-28

---

## 一、测试方法回顾

一次 Play 只测一种条件（模式/渲染器启动即生效），5000 实例（个别 500）、4 套动画轮转分配、每帧全实例公转位移（位置恒变，最严苛的合批/重建条件）、同屏密集堆叠（间距 0.35 < 帧尺寸 0.4~0.6，含大量 overdraw）。

| 模式 | 渲染路径 | 动画驱动方式 |
|---|---|---|
| StaticFrame | GameObject 池 | 不播（隔离"N 个物体每帧动"纯基线） |
| GpuTimeDriven | GameObject 池 | shader 内 `_Time` 自动换帧，CPU 零动画成本 |
| GpuMpbOffset | GameObject 池 | GPU 时间驱动 + 逐实例 MPB 相位偏移（测 MPB 破批） |
| CpuManualFrame | GameObject 池 | CPU 算帧号逐实例 MPB 喂 shader |
| CpuSwap | GameObject 池 | 现有方案：FrameAnimMgr 换 Sprite 引用（仅 SpriteRenderer） |
| GpuInstancing | 无 GameObject | `Graphics.DrawMeshInstanced` 批量提交，逐实例相位/闪白走 instanced buffer |

## 三、数据合理性核验

**结论：数据整体合理、内部自洽，可以用于定案。** 关键交叉验证如下。

### 3.1 通过的核验点

| # | 核验项 | 数据表现 | 判定 |
|---|---|---|---|
| 1 | GPU 时间驱动零 CPU 成本 | Mesh 下 GpuTimeDriven 与 StaticFrame **完全一致**（8.34 / 9.39 / DC 5013 / SetPass 15） | ✅ 符合设计：动画在 shader 内按 `_Time` 计算，CPU 不参与 |
| 2 | DrawCall 计数 | 5013 = 5000 实例 + 13 场景底噪，各模式一致 | ✅ 计数可信 |
| 3 | SRP Batcher 合批 | Mesh + 共享材质 + 无 MPB：SetPass 恒 15；**4 套材质（同 shader）不推高 SetPass** | ✅ 与 Unity 规则一致，确认"多 clip 多材质仍同批"的设计前提 |
| 4 | 逐实例 MPB 破批 | Mesh 下 SetPass 15 → 4529，帧时间 8.34 → 13.27ms（+4.9ms） | ✅ MPB 逐实例提交踢出 SRP Batcher，成本与预期一致 |
| 5 | CPU 手动帧成本 | Mesh 下 CpuManualFrame 13.56ms ≈ GpuMpbOffset 13.27ms | ✅ 两者本质同为"逐实例 MPB"，成本同源；SetPass 3731 < 4529 因帧号取值重复（8 帧 × 4 套仅 32 种状态）复用率更高 |
| 6 | SpriteRenderer 不走 SRP Batcher | 同为静帧：Sprite 19.39ms vs Mesh 8.34ms（-57% FPS）；Sprite DC 2492 < 5000 说明走了 sprite 几何合并，但每帧位置全变导致批几何每帧重建，CPU 反而更重 | ✅ Unity 2022 的 2D 渲染器不支持 SRP Batcher（2023.1 才支持），数据吻合 |
| 7 | MPB 对 sprite 合批的破坏 | Sprite 下 GpuMpbOffset DC 2492 → 4222，26.75ms 全场最差 | ✅ 逐实例 MPB 使 sprite 间无法合并 |
| 8 | CpuManualFrame 在 Sprite 下 ≈ StaticFrame | 19.71 vs 19.39ms | ✅ 已被批重建成本主导，MPB 增量被掩盖（Mesh 下才显形 +5.2ms） |
| 9 | CpuSwap 仅出现在 SpriteRenderer 组 | 数据无 Mesh + CpuSwap 行 | ✅ 与脚本约束一致（Awake 拦截该组合） |
| 10 | GpuInstancing@500 精确吻合 | DC 17 = 13 底噪 + 4 组各 1 个 instanced draw | ✅ 分组与切批逻辑正确 |
| 11 | 最差帧量化 | 16.67=1000/60、33.33=1000/30、41.67=1000/24、25.00=1000/40 | ✅ 典型垂直同步/帧调度量化，非异常尖峰 |

### 3.2 需注意的三点（不影响结论）

1. **120 FPS 行全部触顶**：8.33~8.34ms = 1000/120 即目标帧地板。StaticFrame / GpuTimeDriven(Mesh) / GpuInstancing 之间的真实差异被帧率上限掩盖，本轮只能得出"均 ≤ 8.34ms"，无法相互排序。
2. **GpuInstancing@5000 的 DC 53 高于理论值**：4 组 × ceil(1250/1000) = 8 个 instanced draw + 13 底噪 ≈ 21，实测 53。疑似图形 API 层对大批 instanced draw 做了拆分，建议 Frame Debugger 复核；即便按 53 计也仅为逐实例路径（5013）的 1%，不影响结论。
3. **CpuSwap 场景底噪不同**：该模式必须从正常游戏流程启动（需 GameMgr.Init 注册 FrameAnimMgr），运行环境与裸测试场景不一致；其 SetPass 2506 ≈ DC（逐批切换）建议统一场景复测一次。相对排序（快于 SpriteRenderer+GPU shader、慢于 Mesh+GPU）不受影响。

## 四、对比统计（5000 实例，以 MeshRenderer 静帧为基准）

### 4.1 帧时间与 FPS

| 方案 | 平均帧时间 | 相对基准增量 | FPS | 相对基准 |
|---|---|---|---|---|
| **Mesh + GPU 时间驱动** | **8.34ms** | **+0.00ms** | **120** | **±0%** |
| GpuInstancing（DrawMeshInstanced） | 8.34ms | +0.00ms（触顶） | 120 | ±0% |
| Mesh + CPU 手动帧（MPB） | 13.56ms | +5.22ms | 74 | -38% |
| Mesh + 逐实例 MPB 相位 | 13.27ms | +4.93ms | 75 | -38% |
| Sprite + CpuSwap（现有方案） | 15.51ms | +7.17ms | 64 | -47% |
| Sprite + GPU 时间驱动 | 19.34ms | +11.00ms | 52 | -57% |
| Sprite + CPU 手动帧（MPB） | 19.71ms | +11.37ms | 51 | -58% |
| Sprite + 逐实例 MPB 相位 | 26.75ms | +18.41ms | 37 | -69% |

### 4.2 渲染提交规模

| 方案 | DrawCalls | SetPass | 说明 |
|---|---|---|---|
| GpuInstancing | **53**（-98.9%） | 20 | 唯一真正合并 draw 的路径；逐实例属性走 instanced buffer 不破批 |
| Mesh 全系（无 MPB） | 5013 | **15** | SRP Batcher：DC 不降但 SetPass 恒定，CPU 提交成本低 |
| Sprite 全系 | 2492~4222 | 15~2506 | sprite 几何合并降 DC 但每帧重建；MPB 即破合并 |

### 4.3 关键量化结论

1. **GPU 时间驱动 = 免费**：与静帧逐字节一致（8.34/9.39ms），"用 GPU 每像素 ALU + 2 次数据纹理点采样换掉 C# 逐帧推进 + 换帧"成立。
2. **逐实例 MPB 的代价 ≈ +5ms/5000 实例**（SetPass 15 → 4 千级），Mesh 与 Sprite 双双验证。
3. **SpriteRenderer 路线系统性劣势 ≈ +11ms/5000 实例**（无 SRP Batcher + 批几何每帧重建），与动画方案无关，是渲染器本身的问题。
4. **CpuSwap 在 Sprite 内最快（15.51ms）但整体仍不敌 Mesh+GPU（8.34ms，慢 86%）**：其优势来自 Sprites/Default 极简片元，而非驱动方式。
5. **GpuInstancing 提交规模压缩 99%**，且 5000 实例矩阵逐帧 CPU 更新仍在预算内（触顶 8.34ms）。
6. GPU 时间驱动的成本在**片元侧**（数据纹理采样 + 矩形重映射 + 分支透明），Sprite 数据已显现其片元开销（15.51 → 19.34ms），极端 overdraw 场景需留意（见后续验证）。

## 五、定案：渲染方案选型

### 5.1 方案矩阵

| 场景 | 同屏量级 | 定案方案 | 依据 |
|---|---|---|---|
| 常规序列帧（界面特效/场景装饰/角色） | < 3000 | **A. GPU 时间驱动 + MeshRenderer + 每 clip 共享材质**（Game/FrameAnimGpu，SRP Batcher） | 5000 实例仍与静帧完全一致，SetPass 恒 15，最差帧 9.39ms 稳定 |
| 高密度（3000~5000） | 3000~5000 | A（已验证 5000 触顶）；低端机复测后如 DC 5000 超预算则降级 B | DC 随实例线性（5013@5000），提交成本是唯一变量 |
| 海量（>5000：弹幕/飘字/群体特效） | > 5000 或需逐实例相位/闪白 | **B. GPU Instancing**（DrawMeshInstanced + Game/FrameAnimGpuInst） | DC -99%（53@5000），触顶 8.34ms；逐实例属性走 instanced buffer 不破批 |
| 少量需精确控制（暂停/步进/播完回调） | < 300 | A 的手动帧模式（MPB 喂 `_FrameIndex`）或维持现有 CpuSwap | MPB 破批成本在百级实例可忽略 |
| 存量 CpuSwap 功能 | - | **保留为兼容层，不再扩展** | 15.51ms@5000，仅 SpriteRenderer 可用，SetPass 2506 |

### 5.2 各方案落地约束

**方案 A（主力）**
- 渲染器必须 MeshRenderer（FrameAnimGpuClip.QuadMesh 已备好）；SpriteRenderer 仅作过渡。
- 同一 clip 的全部实例共享同一个 Material 实例（合批前提）；多 clip 多材质同 shader 仍同批，SetPass 不涨（已验证）。
- **禁止逐实例 MPB**（相位/手动帧/闪白都会踢出 SRP Batcher）。逐实例差异一律走"每实例材质克隆"承载：同 shader 多材质不涨 SetPass（已实测，怪物场景详见第六节）。
- 暂停/加减速/整体染色走共享材质属性，一次设置全实例生效。
- 真机需先经 Addressable 显式加载 shader（FrameAnimGpuUtil.FindShader 已处理），或进 Always Included Shaders。

**方案 B（海量）**
- 无 GameObject：没有 Transform 挂点、物理、点击、动画间排序（半透 ZTest LEqual，实例间无深度写入），仅适合"一层幕布式"海量同质元素。
- 矩阵每帧 CPU 更新 + draw 每帧重新提交（DrawMeshInstanced 语义），5000 实例已验证在预算内。
- 与 SRP Batcher 互斥（独立 shader 变体），只对大批量启用，勿与 A 混用于同屏主路径。

**方案 C（兼容层）**
- FrameAnimMgr/FrameAnimPlayer 维持现状服务存量；新功能一律走 A/B。

### 5.3 决策速查

```
同屏序列帧数量 N？
├─ N < 300 ──────── 任意方案均可 → 统一走 A
├─ 300 ~ 5000 ───── A（GPU 时间驱动 + MeshRenderer + 共享材质）
│                    └─ 需逐实例相位/闪白？→ 少量克隆材质 _StartFrame；
│                       大量 → 升 B
├─ N > 5000 ─────── B（DrawMeshInstanced + FrameAnimGpuInst）
└─ 需播完回调/精确暂停（少量）→ A 手动帧 MPB，或维持 CpuSwap
```

## 六、怪物场景专项：逐怪差异在 SRP 合批内的承载方案

怪物需求五条：刷新即播第一帧、动作不能同步、待机/移动/攻击切换、受击闪白、减速只降移动动画速度。

### 6.1 结论：全部可保 SRP 合批

破批通道**只有逐实例 MPB**（实测 SetPass 15 -> 4529）；SRP Batcher 按 **shader** 合批，材质属性值不同、不同 Material 实例均不破批（实测 4 套材质 SetPass 恒 15）。
承载方式：**每怪每 clip 一个材质克隆（随怪池化）**，逐怪差异全部走材质属性，切换动画 = renderer 换 `sharedMaterial` 引用。

### 6.2 需求 -> 材质属性映射

| 需求 | 承载属性 | 设置时机 | 破批？ |
|---|---|---|---|
| 刷新即播第一帧 | `_FrameOffset = -Time.time × fps × speed`（GPU 帧号恰为 0） | 出生 | 否 |
| 动作不能同步 | 同上（出生时刻不同天然错相）；同波同时出生再叠加随机 offset | 出生 | 否 |
| 待机/移动/攻击切换 | 每怪每 clip 一个材质克隆，切换 = 换 `sharedMaterial`（同 shader 不破批） | 状态机 | 否 |
| 受击闪白 | `_FlashAmount`（已补进 FrameAnimGpu 的 UnityPerMaterial），命中期间逐帧衰减，只触碰闪白中的怪 | 受击 | 否 |
| 减速只降移动动画 | 只改"移动 clip"克隆的 `_PlaySpeed`，待机/攻击材质不动 | 减速/解除 | 否 |

### 6.3 关键公式与 CPU 镜像

- 变速防相位跳变：`新offset = 旧offset + T × fps × (旧速度 − 新速度)`（T = 当前时刻，保证变速瞬间帧号连续）
- GPU 时间驱动无播完回调：攻击判定位、播完回待机由 CPU 承担--镜像帧号 `floor((T − t0) × fps × speed)`（与 shader 同源），或直接按技能计时器驱动，动画仅做表现
- 闪白衰减 / 变速 / 换帧都只是改材质数值，不触碰合批状态

### 6.4 代价与真正失守的边界

| 代价 | 说明 |
|---|---|
| DC 仍 = 怪数 | SRP Batcher 不合并 draw；怪量级（同屏几十~几百）无压力，实测 5000 draw 亦触顶 |
| 材质实例内存 | 每怪 × clip 数个克隆（纹理为共享引用，无 GPU 重复），随怪池化复用 |
| 逻辑复杂度 | 换动画/变速时的 offset 补偿、CPU 镜像帧号维护 |

真正失守只有一种情况：**同屏数千怪 + 低端机 DC 预算紧** -> 升 Instancing（B 方案）：`_FrameOffset`/`_FlashAmount` 逐实例已在 FrameAnimGpuInst，逐实例 `_PlaySpeed` 加一个 instanced 属性即可，换动画 = 实例在 clip 分组间迁移；代价是无 GameObject、无逐实例排序。

## 八、一句话总结

**定案：常规量级走"GPU 时间驱动 + MeshRenderer + 共享材质"（SRP Batcher，5000 实例与静帧零差异），海量（>5000 或需逐实例相位/闪白）走 DrawMeshInstancing（DC 压缩 99%）；SpriteRenderer 路线与逐实例 MPB 因 -38%~-69% FPS 全部禁用，CpuSwap 降级为兼容层。怪物逐怪差异（第一帧起播/错相/换动画/闪白/减速）全部走每怪材质克隆承载，仍在同一 SRP 批内（见第六节）。**
